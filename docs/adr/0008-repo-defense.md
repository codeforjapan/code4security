# ADR 0008: このリポジトリを、利用者に届くものの供給元として守る

## ステータス

提案中

## 日付

2026-10-16

## コンテキスト

このリポジトリから配るものは、利用者の環境で動くか、利用者のエージェントに読まれる（[ADR 0004](0004-repo-role-and-distribution.md)）。

- plugin の MCP サーバーは、利用者の PC で、利用者の `gh` の認証を使って動く
- skill と項目データ（`setup`・`verify`・`how.command`）は、エージェントが読んで実行する
- 設定のひな形は、利用者のリポジトリに写される
- checker の action は、利用者の Actions で、リポジトリを読めるトークンを使って動く

ここが改ざんされたり、悪意のある変更がマージされたりすると、利用者全員に一度に広がる。セキュリティの点検を勧めるプロジェクトなので、狙われたときの影響も、信頼を失ったときの影響も大きい。

## 決定

次の箇所を、このリポジトリの守るべき面として扱う。v1 の公開までに、それぞれの対策を Issue にして決める。

### 問題になりそうな箇所

| 箇所 | 何が起きうるか | 対策の方向 |
|---|---|---|
| **plugin の配布** | main に入った変更が、そのまま利用者に届く（相対パスの plugin は、マーケットプレイスのリポジトリの版に従う） | 利用者には tag を指定して追加するよう案内する。リリースの手順を決め、main と配布する版を分ける |
| **MCP サーバー** | 利用者の PC でコードが動く。`verify` の `command` を通して任意のコマンドが動く | `command` は読み取りだけのものに限るとレビューの基準に書く。実行の前にオーナーに見せる。MCP サーバーが動かせるコマンドを決めておく |
| **項目データと skill の文章** | エージェントへの指示を紛れ込ませる（プロンプトインジェクション）。危険なコマンドや、攻撃者の用意した URL を勧める | `setup`・`verify`・`how.command`・`sources.yml` の URL の変更は、コアメンバーのレビューを必須にする（CODEOWNERS） |
| **設定のひな形** | 利用者のリポジトリに、危険な workflow（強すぎる `permissions`、`pull_request_target` の誤用、固定していない action）が写される | ひな形にも zizmor をかける。外部の action は SHA で固定する |
| **checker の action** | 利用者のトークンでリポジトリを読める。改ざんされると、利用者のコードやアラートが外に持ち出される | 利用者には SHA で固定してもらう。action の変更はコアメンバーのレビューを必須にする |
| **依存パッケージ** | npm などの依存が乗っ取られ、plugin・checker を通して利用者に届く | 依存を最小限にする。lockfile を固定し、Dependabot の cooldown を使う。plugin に入れる依存は特に絞る |
| **このリポジトリの CI** | PR から secrets や書き込みの権限を盗まれる。`GITHUB_TOKEN` の権限が強すぎる | 既定の `permissions` を読み取りだけにする。fork からの PR で secrets を使わない。自分の workflow にも zizmor をかける |
| **メンテナのアカウント** | 乗っ取られると、レビューを素通りして変更できる | 2FA を必須にする。管理者を最小限にする。ruleset で main への直接の push と、レビューなしのマージを禁じる |
| **リリースとタグ** | タグを付け替えて、別のコードを配る | タグを保護する（ruleset）。リリースのコミットの SHA を公開する |
| **自動化の PR**（README の第 10 節） | 委譲先の監視や版の更新を自動でマージする流れが、悪意のある変更の通り道になる | 自動でマージしてよい変更の範囲を、パスと変更の種類で決める。推奨の変更は自動でマージしない |
| **イベントや、初めてのコントリビューター** | 短い期間に多くの PR が来て、レビューが追いつかず、危険な変更が紛れる | 初めての人の PR は、Actions の実行に承認を必須にする。守るべきパスは CODEOWNERS で分ける |
| **資料の URL** | 項目が参照するドメインが失効し、第三者に取られる | `evidence.checked` が古いものを定期的に見直す。リンク切れを CI で確かめる |
| **脆弱性の報告** | このリポジトリ自体の穴を、公開の Issue で報告されてしまう | SECURITY.md で非公開の窓口（GitHub の private vulnerability reporting）を案内する |

## 根拠

- 配るものの多くは、利用者の権限で動くか、エージェントに指示として読まれる。ふつうの OSS より、守るべき面が広い
- 企画書の第 10 節で、推奨の自動採用はサプライチェーンの侵入面になると決めている。それを、このリポジトリ自体にも当てはめる
- 自分のリポジトリで守りを回せていなければ、利用者に勧める説得力がない。このリポジトリを最初の利用者にする

## 影響

### メリット

- 守るべき箇所が一覧になり、対策を Issue として分けて進められる
- このリポジトリで行う対策が、そのまま項目データやひな形の試験になる

### 懸念点

- レビューを必須にする箇所が多く、コアメンバーの負担が大きくなる
  - 緩和策: CODEOWNERS で、守るべきパス（`plugin/server/`・`checker/`・`plugin/templates/`・項目の `setup` と `verify`）だけに絞る。文章だけの変更は、ふつうのレビューで通す
- 初めてのコントリビューターが入りにくくなる
  - 緩和策: 守るべきパス以外は、今までどおり入りやすく保つ。good first issue は、守るべきパスの外から選ぶ

## 代替案

- **v1 のあとに考える**: v1 までの作業は減る。一方で、イベントで多くの人に plugin を入れてもらった後に穴が見つかると、取り返しがつかない
- **すべての変更でコアメンバーのレビューを必須にする**: 守りは強い。一方で、コアメンバーが詰まり、非同期で進めにくくなる

## 今後の方向性

- 上の表の各行を Issue にし、v1 の公開までに対策を決める
- このリポジトリに、このプロジェクトの点検（plugin）を最初に当てはめる
- 見直すきっかけ: 利用者や、checker を参照するリポジトリが増えたとき。外部の専門家のレビューを受けられるようになったとき
