# ADR 0003: v1 は「AI といっしょに自分のプロジェクトを点検し、設定まで終える」ところまでにする

## ステータス

承認済み

## 日付

2026-10-16

## コンテキスト

12/12（土）のイベントで v1 を公開し、参加者がその場で自分のプロジェクトに基本の守りを入れることを目指している。準備期間は 8 週間ほどで、開発はコントリビューターが非同期で進める。

点検表の Viewer は、AI ですぐに作り直せる。手間がかかっていて、ほかにないのは「自分のプロジェクトに当てはめて、実際に設定し終える」部分である。

## 決定

v1 では、プロジェクトオーナーが手元の AI エージェント（Claude Code・Cursor・Codex など）と、次の流れを最後まで進められるようにする。

1. **点検表を完成させる**: エージェントがリポジトリを調べて当てはまる条件を推測し、推測できない条件はオーナーに聞く。対象の項目ごとに、済み・未着手・対象外・リスクを受け入れる、を決める
2. **脅威モデルを作る**: 条件（扱うデータ・使っているサービス）と項目の状態から、守るもの・入り口・脅威・残っている穴をまとめる
3. **回し続ける項目を知る**: コミット時（Gitleaks + lefthook）、PR 時（CodeQL・zizmor）、毎週（checker）などのルーチンを一覧にする
4. **項目ごとに設定する**: エージェントがキットのテンプレを使って設定し、確かめ方の手順で済んだことを確かめる。変更はオーナーが 1 件ずつ承認する

v1 に含めるもの:

- `guide/`: 項目データとスキーマ v2（[ADR 0005](0005-schema-v2-and-project-state.md)）
- `agent/`: 上の 1〜4 を進める、エージェント向けの手順（特定の AI 製品に依存しない本文と、製品ごとの薄い入り口）
- `kit/`: ルーチン項目の設定テンプレ
- `checker/`: 毎週の横断チェック
- 日本語の導入手順書

v1 に含めないもの:

- Viewer の作り直し（今の `index.html` はそのまま動かす）
- CLI（設計は ADR で残す）
- 他人の OSS を見て回る取り組みと、修正への報酬

GitHub 以外（Slack・Google Workspace・Notion・独自ドメインなど）の項目も v1 に入れる。CfJ の運営に必要なので CfJ のメンバーが担当し、Issue にはするがコミュニティには依頼しない（`cfj-internal` ラベル）。

## 根拠

- 小規模なチームが止まるのは「何をやるか分からない」ことより、「自分のプロジェクトだと何が当てはまり、どう設定するのか」のところ。そこをエージェントが埋めれば、1 日で導入するという目標に届く
- Viewer は見た目の問題で、データがそろえば後から何度でも作り直せる。限られた期間は、データとエージェント向けの手順に使う
- エージェント向けの手順を特定の製品に依存させなければ、参加者が普段使っている AI をそのまま使える
- GitHub 以外の項目は、CfJ の実際の運営を知らないと書けず、コミュニティには頼みにくい

## 影響

### メリット

- イベント当日に、参加者が自分のプロジェクトで最後まで進められる
- 項目データに、エージェント向けの欄（`verify`・`setup` など）が加わり、1 項目ずつの小さな PR で貢献できる

### 懸念点

- エージェントの振る舞いは毎回同じにはならず、点検の結果がぶれる
  - 緩和策: 済んだかの判断は `verify` の決まった手順で行い、エージェントの判断に任せる部分を減らす
- エージェントが、オーナーの意図しない変更を加える
  - 緩和策: 設定の変更は 1 件ずつオーナーの承認をもらう手順にする
- Viewer がないと、エージェントを使わない人が入りにくい
  - 緩和策: 今の `index.html` を動かし続け、`checklist.md` も配る

## 代替案

- **Viewer と点検表を v1 の中心にする**: 見た目で伝わりやすいが、「読んだあと設定しない」状態が残る。AI で作れる部分に時間を使うことになるので採らない
- **CLI を作り、決まった手順で設定する**: 結果は安定するが、プロジェクトごとの違いに対応する分岐を作り込む必要があり、期間内に終わらない。CLI は ADR で設計だけ残す

## 今後の方向性

- v1 のあとに、Viewer の作り直し（`project.yml` を読み込んで表示するなど）、CLI の設計、他人の OSS を見て回る取り組みを検討する
- イベントで導入にかかった時間と、詰まった場所を記録し、v1 の範囲を見直す材料にする
