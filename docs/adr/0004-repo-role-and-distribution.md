## コンテキスト

実際の設定（`lefthook.yml`・`.github/workflows/*.yml`・`dependabot.yml`）は、各プロジェクトのリポジトリに置かれる。このリポジトリに何を置き、どう配るかを決める必要がある。

v1（[ADR 0003](0003-v1-scope.md)）では、プロジェクトオーナーが手元の AI エージェントといっしょに点検から設定まで進める。はじめの案では、エージェント向けの機能を skill と MCP サーバーをまとめた plugin として配るつもりだった。

2026-10-30 の打ち合わせで、plugin で配ることについて次の点が挙がった。

- plugin の入れ方はエージェントごとに違い、エージェントごとに手順を用意しないと使ってもらえない
- plugin を入れると、利用者は、このリポジトリのコードを自分の PC で動かすことになる。利用者はこのリポジトリを信頼する必要があり、こちらは配ったものを保守し続ける必要がある
- 点検で中心になるのは「どの観点で、何を確かめ、どう設定するか」で、それは Markdown に書ける。plugin は、その Markdown を包んだものにすぎない

## 決定

### 1. このリポジトリの役割

このリポジトリは、プロジェクトに守りを入れるための材料を配る。

| このリポジトリに置くもの | 各プロジェクトのリポジトリに置かれるもの |
|---|---|
| 項目データ・スキーマ・`checklist.json`・`checklist.md`（`guide/`） | なし（公開しているものを読む） |
| 対策ごとの Markdown（`agent/`。何を・なぜ設定するか、使えるツール、公式ドキュメントとセットアップガイドへのリンク） | なし（公開しているものを読ませる） |
| 設定のひな形（持つかは [#33](https://github.com/codeforjapan/code4security/issues/33) で決める） | エージェントが書いた `lefthook.yml`・workflow・`dependabot.yml` |
| 参照される部品: checker の action（`checker/`） | `uses: codeforjapan/code4security/checker@<sha>` を書いた、数行の呼び出し側の workflow |
| ADR・ロードマップ・導入手順書（`docs/`） | なし |

このリポジトリ自体の lefthook や Actions は、このリポジトリを守るための設定で、上の表とは別に扱う（[ADR 0008](0008-repo-defense.md)）。

### 2. v1 では plugin・skill・MCP サーバーを作らず、Markdown を配る

このリポジトリは、対策ごとに Markdown を書いて公開する。1 つの Markdown には、次のことを書く。

- 何を設定する必要があるか、なぜ必要か（OWASP・IPA などの参照先へのリンクを含む）
- 使えるツールの例
- 各ツールの公式ドキュメントと、セットアップガイドへのリンク

例：「API キーやパスワードをコミットしないよう、コミットのときに確認する仕組みを入れる。漏れたキーは悪用され、消しても履歴に残るためである。使えるツールには Gitleaks などがある。公式ドキュメントはここ、セットアップガイドはここ」

利用者は、この Markdown を自分のコーディングエージェントに読ませ、自分のリポジトリに設定してもらう。エージェントは、Markdown に書かれたリンク先の公式ドキュメントやセットアップガイドを読んで、プロジェクトに合わせて設定を書く。書く前に、オーナーに差分を見せて承認をもらう。

Markdown は、利用者のリポジトリにコピーせず、このリポジトリで公開しているものを読ませる（たとえば、Markdown の URL をエージェントに渡して「これを読んで、このリポジトリに設定して」と頼む）。こうすると、このリポジトリで誤りを直したり、対策を足したりすれば、利用者は何もしなくても、次にエージェントに読ませたときから新しい内容で設定できる。

- 内容が変わると点検の結果も変わるので、版を固定したい人のために v1 のタグを打ち、タグを指定した URL も案内する
- 公式ドキュメントとセットアップガイドを示すのに加えて、このリポジトリで設定のひな形も持つかは、[#33](https://github.com/codeforjapan/code4security/issues/33) で決める
- plugin・skill・MCP サーバーにまとめるのは、v1 のあとに、Markdown の中身が固まってから考える

### 3. 設定は「写す」を基本にし、ロジックを持つ部品だけ「参照させる」

- **写す**: lefthook・CodeQL・zizmor・Dependabot の設定。エージェントが、Markdown とそのリンク先の公式ドキュメントやセットアップガイドを読んで、プロジェクトに合わせて書き、利用者のリポジトリに置く。オーナーが中身を読める長さに保つ。このリポジトリで設定のひな形も持つかは [#33](https://github.com/codeforjapan/code4security/issues/33) で決める
- **参照させる**: checker の action だけ。コミットの SHA で固定してもらい、更新は Dependabot で届ける

### 4. 守りは重ねてよい

GitHub の secret scanning と、lefthook で動かす Gitleaks のように、同じ穴を塞ぐ対策が重なってもよい。どれか 1 つが漏らしても、ほかで止まればよい（スイスチーズモデル）。Markdown では「GitHub がやってくれるから要らない」とは書かず、重ねて入れることを勧める。

### 5. 特定のエージェントに依存しない

- Markdown は、特定のエージェントでしか動かない書き方をしない。ファイルを読み、コマンドを動かし、ファイルを書けるエージェントなら使える形にする
- ファイルの変更やコマンドの実行の前に、差分やコマンドをオーナーに見せて承認をもらう、と Markdown に書く。エージェントの機能には頼らない

### 6. 対応する場所と、できること

v1 はコーディングエージェントを使うことを前提にする（[ADR 0003](0003-v1-scope.md)）。

| | 点検・脅威モデル | ルーチンの提案 | 設定・確かめる |
|---|---|---|---|
| コーディングエージェント（Claude Code・Codex・Cursor・GitHub Copilot など） | ○ | ○ | ○ |
| チャットだけ（claude.ai・ChatGPT など） | ○（聞き取りだけ） | ○ | Markdown とリンク先を読み、自分で設定する |

Claude Code・Codex・Cursor・GitHub Copilot で使えるようにし、イベントの前にこの 4 つで最後まで試す（[ADR 0003](0003-v1-scope.md)）。

### 7. リモートの MCP サーバーは作らない

CfJ がサーバーを運営すると、利用者の「まだ対策していない穴」の情報がそこに集まる。v1 では MCP サーバー自体を作らないが、のちに作るときも手元で動くものだけにする。

## 根拠

- 実際の設定を持つのはプロジェクトのリポジトリなので、このリポジトリは「材料を配る」役に絞ると、何をどこで直すかが分かりやすい
- Markdown なら、どのエージェントでも同じものを読める。エージェントごとの入れ方の手順を用意しなくて済み、v1 の準備期間（12/19 まで）に収まる
- 利用者の PC でこのリポジトリのコードを動かさないので、利用者が信頼しなければならない範囲と、こちらが保守する範囲が小さい
- 短い設定は、写したほうがオーナーが読めて、このリポジトリへの依存も増えない。checker は中身が大きく、直したときに全員へ届けたいので、参照させる
- 小さな事故（API キーのコミットなど）は、メンバーが入れ替わったときに起きやすい。1 回の点検で終わらせず、コミット時の確認などの仕組みを重ねて入れておくほうが確か
- 弱点の情報を CfJ が預からなければ、守るべきものと運営の手間が増えない

## 影響

### メリット

- 参加者が普段使っているエージェントで、何も入れずにそのまま使える
- 点検の観点を、小さな PR で直せる。コードを書かない人も、Markdown を直して貢献できる
- このリポジトリで Markdown を直せば、利用者が次にエージェントに読ませたときから、直した内容が使われる

### 懸念点

- エージェントの振る舞いは毎回同じにはならず、点検の結果がぶれる。MCP サーバーで確かめ方を固める案より、ぶれは大きい
  - 緩和策: 項目の `verify` に、決まった確かめ方（読むファイル・叩く API・動かすコマンド）を書き、Markdown ではそれに従うよう指示する
- 公開している Markdown が改ざんされると、それを読んだ利用者のエージェントが、意図しない変更を加えるおそれがある
  - 緩和策: 変更の前に必ずオーナーの承認をもらう、と Markdown に書く。`agent/` を守るべきパスにする（[ADR 0008](0008-repo-defense.md)）。版を固定したい人にはタグを指定した URL を案内する
- 写した設定は、あとから推奨が変わっても利用者に届かない
  - 緩和策: 届ける仕組みは v1 のあとに考える。書くときの材料をどうするか（[#33](https://github.com/codeforjapan/code4security/issues/33)）とあわせて、古くなったことに利用者が気づける方法を考える
- コーディングエージェントを使っていない人が入りにくい
  - 緩和策: 前提を最初に書いておく。このプロジェクトが、エージェントを使い始めるきっかけになるようにする（[ADR 0003](0003-v1-scope.md)）

## 代替案

- **skill と MCP サーバーをまとめた plugin として配る**（この ADR のはじめの案）: Claude Code では入れるのも更新するのも簡単で、MCP サーバーで確かめ方を固められる。一方で、エージェントごとに入れ方の手順が要り、利用者の PC でこのリポジトリのコードが動く。v1 の準備期間と、配ったものを保守し続ける手間に見合わないので、v1 のあとに回す
- **CLI を作り、決まった手順で設定する**: 結果は安定するが、プロジェクトごとの違いに対応する分岐を作り込む必要があり、期間内に終わらない（[ADR 0003](0003-v1-scope.md)）
- **設定をすべて参照させる**（reusable workflow・lefthook の remotes）: 更新が全員に届く。一方で、このリポジトリへの依存と、改ざんされたときの影響が大きくなる。短い設定ではオーナーが中身を読まなくなる

## 今後の方向性

- `agent/` に置く Markdown の分け方（観点ごとに 1 つか、まとめて 1 つか）は、点検表の項目の整理（[#21](https://github.com/codeforjapan/code4security/issues/21)）とあわせて決める
- [ADR 0005](0005-schema-v2-and-project-state.md)〜[ADR 0009](0009-cyberriskscape.md) にある plugin・MCP サーバーの記述（`plugin/templates/`、手元のルートを MCP サーバーにすることなど）を、この決定に合わせて直す
- v1 のあとに、plugin・skill・MCP サーバーにまとめるかを考える。見直すきっかけ: Markdown の中身が固まったとき、エージェントによって結果のぶれが大きく、確かめ方を固める必要が出たとき、Agent Plugins のような共通の仕様が広く使われるようになったとき
- 写した設定の更新を届ける方法（「今の推奨との差分を確かめる」手順など）を検討する
