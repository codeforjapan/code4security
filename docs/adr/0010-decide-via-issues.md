## コンテキスト

[PR #1](https://github.com/codeforjapan/code4security/pull/1) で、ADR 0001〜0009 を一度に main に入れた。0003 以外は `提案中` で、意見を集めている途中だった。

意見の宛先は 2 通りに分かれていた。ADR 0001 の注記は「意見は Issue か Slack のチャンネルへ」、PR #1 の本文は「コメントで意見をください」としていた。PR のコメントはマージすると流れ、ADR の側から辿れない。

決めたことの経緯も残っていない。[ADR 0003](0003-v1-scope.md) は `承認済み` だが、誰がいつどこで決めたかが書かれておらず、テンプレートにも書く場所がない。

開発は非同期で進め（[roadmap](../roadmap-v1.md)）、参加する人には、コードを書かずに文章だけを直す人もいる（[ADR 0006](0006-schema-definition.md)）。

2026-10-18 の打ち合わせで、次のことを決めた（[記録](https://github.com/codeforjapan/code4security/pull/1#issuecomment-6246409230)）。

- 既存の ADR は、たたき台として取り込む
- 答えを出す必要がある論点は、別にイシューに切って検討する
- 決まったことは、ADR に記録を残していく

## 決定

1. **`提案中` の ADR は、たたき台として main に残す**。意見を集めるときは、本文から議論するイシューにリンクする
2. **答えを出す必要がある論点は、1 つの論点に 1 つのイシューで議論する**。イシューのテンプレート「論点（決めること）」を使う
3. **決まったら ADR に残す**。ADR を書く（またはステータスを上げる）PR を出し、その PR で論点のイシューを閉じる。PR のレビューの approve を合意の記録とし、ADR の「決定の記録」に、議論したイシュー・決定の場・承認者・承認日を書く
4. **Slack や打ち合わせで決まったことは、まず論点のイシューにコメントで戻す**。そのうえで ADR に落とす
5. **書けば済むもの（事実の訂正、ADR の間の記述の整合）は、イシューを立てずに、ADR を直す PR を出す**
6. **議論の場は、GitHub Discussions ではなく Issues にする**

## 根拠

- **書き込みやすさ**: PR のレビューは、コードを読む人には慣れた形だが、文章に一言コメントしたい人には重い。イシューならコメント欄に書くだけで済む
- **粒度**: 1 つの PR に複数の ADR が入ると、どこにコメントすればよいか分からない。PR #1 は、レビュアーを決めないまま、しばらくコメントが付かなかった。1 つの論点が 1 つのイシューなら、自分が答えられるものだけを開ける
- **未決の一覧**: open のイシューが、そのまま決まっていない論点の一覧になる。ラベルとマイルストーンで、領域と期限も分かる
- **承認の記録**: ADR を上げる PR の approve は、誰がいつ賛成したかとして GitHub に残る
- **先例**: Python の PEP は、本文の `Discussions-To` ヘッダで議論の場を外に指している（[PEP 1](https://peps.python.org/pep-0001/#pep-header-preamble)）。Rust の RFC も、受理された RFC ごとに実装を追う issue を別に持つ（[rust-lang/rfcs](https://github.com/rust-lang/rfcs#implementing-an-rfc)）

## 影響

### メリット

- 議論と決定が、双方向のリンクで辿れる（イシューから ADR の PR、ADR の「決定の記録」から元のイシュー）
- 決まったことと決まっていないことの区別が、ADR のステータスとイシューの open / closed で見える

### 懸念点

- イシューと ADR の 2 か所を行き来することになる
  - 緩和策: 双方向にリンクする。ADR の「決定の記録」に元のイシュー、イシューの側には ADR の PR（`Closes` で閉じる）
- Slack や打ち合わせで決まったことが、イシューに戻らない
  - 緩和策: 決まった直後に、要点を論点のイシューにコメントする。PR #1 の打ち合わせの記録がその例
- 誰の approve で `承認済み` とするかが、まだ決まっていない
  - 緩和策（案）: 当面は、論点を立てた人以外のコアメンバー 1 人以上の approve とする。この PR のレビューで決めたい

## 代替案

- **PR を議論の場にする（RFC 型）**: ADR を足す PR で議論し、マージで承認とする。approve がそのまま合意の記録になる。一方で、本文を直すと行に付いたコメントが古い扱いになり読みにくくなる。文章だけ直す人には、書き込むまでが重い
- **イシューだけで決め、ADR を書かない**: 手軽だが、なぜそう決めたかを後から知るには、スレッドを読み返すしかない
- **GitHub Discussions を議論の場にする**: スレッドや回答の印が使える。一方で、PR から `Closes` で閉じられず、ラベルやマイルストーンとも合わせにくい

## 今後の方向性

- イシューの種類・ラベル・マイルストーンの具体は、CONTRIBUTING に書く
- 誰の approve で `承認済み` とするか（人数と役割）を、運用しながら決める
- 見直すきっかけ: 論点のイシューが増えて追いきれなくなったとき。コアメンバーが増え、承認の基準を決め直す必要が出たとき
