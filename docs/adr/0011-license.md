# ADR 0011: コードとプロジェクトの文書は MIT、利用者や顧客に渡るガイダンスは CC BY 4.0 にし、出力に出典を入れる

## ステータス

提案中

## 日付

2026-10-20

## コンテキスト

`main` に LICENSE がなく、ライセンスの記述が 3 か所で食い違っていた。

- README 第 8 節：「MIT または Apache-2.0」（未決定）
- [ADR 0002](0002-import-yokinist-repos.md)：取り込む 2 つのリポジトリのライセンスを引き継ぐ（コードは MIT、`guide/data/` などの文章とデータは CC BY 4.0）
- [ADR 0009](0009-cyberriskscape.md) の代替案：CyberRiskScape（Apache-2.0）の脅威ルールを、帰属表示をして取り込む案

取り込みの PR より前に、どのパスがどのライセンスかを決めておく必要がある。

あわせて、守りたいことが 1 つある。セキュリティ会社などがこのキットを使って第三者に役務を提供するとき、その第三者（顧客）が Code for Security の存在を知れるようにしたい。

この点で、ライセンスごとにできることは次のとおり。

- MIT・MPL・GPL：義務が生じるのはソフトを配るときだけ。社内で動かして結果だけを渡すなら、何の義務もない
- AGPLv3：義務が生じるのは、改変した版をネットワーク越しに直接使わせるときだけ。報告書を渡すだけなら当たらない
- CC BY 4.0：こちらの文章やデータを報告書に入れて渡すと、「共有」にあたる。出典の表示と、変更したならその旨の記載が必要になる

## 決定

### 1. ライセンスは MIT と CC BY 4.0 の 2 種類にする

- コードとプロジェクトの文書（設定のひな形・`.github/`・README・CONTRIBUTING・AGENTS.md・ADR・ロードマップを含む）：MIT。著作権者は「Code for Japan and contributors」
- 利用者や顧客に渡るガイダンスの文章とデータ：CC BY 4.0。対象は点検項目、点検の結果や報告書のひな形
- 線引きは「利用者や顧客に渡るガイダンスかどうか」の 1 本にする。ADR などのプロジェクトの文書は、何をどう決めたかの記録で、報告書に入るものではないので MIT にする
- ルートに `LICENSE`（MIT）と `LICENSE-CONTENT.md`（CC BY 4.0。対象と出典の示し方）を置く
- パスごとの一覧は README 第 8 節に置く。一覧にないものは、コードとプロジェクトの文書として扱い、MIT にする

### 2. 取り込むものは、元の著作者の表示を残す

- `guide/LICENSE`・`guide/LICENSE-CONTENT.md`・`checker/LICENSE` を消さずに置く。ルートの `LICENSE` には併記しない
- `guide/` の文章とデータを使う人は、`guide/LICENSE-CONTENT.md` の示し方に従う

### 3. 出典の示し方を決め、出力物に最初から入れる

- 出典は TASL（題名・著作者・出典・ライセンス）の 4 つで示す。書き方の例は `LICENSE-CONTENT.md` に置く
- 利用者や顧客の手に渡る出力物（`checklist.md`、checker が起票する Issue、報告書のひな形など）の末尾に、出典の行を最初から入れておく

## 根拠

- 顧客に渡るのは、ソフトではなく報告書や点検の結果。そこに届くのは CC BY 4.0 だけで、コードをコピーレフトにしても目的には効かない
- 報告書に入るもの（点検項目・ひな形）を CC BY 4.0 にし、出典の行を最初から入れておけば、消すことがライセンス違反になる。表示を残してもらいやすい
- 書き方を決めておくと、守る側は迷わず、守られていないときも指摘しやすい
- 取り込む 2 つのリポジトリと同じライセンスなので、yokinist さんへの確認がほぼ要らず、取り込みの PR（10/24 が目安）に間に合う
- 利用者は設定のひな形を自分のリポジトリに写して使う。MIT なら、写した側が別のライセンスに巻き込まれる心配がなく、導入しやすい
- ライセンスの境目が「利用者や顧客に渡るガイダンスかどうか」の 1 本だけなので、コントリビューターが迷いにくい
- MIT はもともと「ソフトウェアとそれに付く文書」を対象にしているので、プロジェクトの文書をコードと同じに扱える

## 影響

### メリット

- 報告書にこちらの文章が入っていれば、役務提供の先の顧客にも出典が伝わる
- `guide/` と `checker/` を、ライセンスを変えずにそのまま取り込める
- GitHub が `LICENSE` を読み取り、リポジトリのライセンスを MIT と表示する

### 懸念点

- ツールを社内でだけ使い、報告書を自社の言葉で書く会社には、出典の表示を求められない
  - 緩和策: 使っただけで表示を求めることは OSS の定義に反するので、ライセンスでは扱わない。必要になったら、名前やロゴの商標と、表示のしかたのルールで扱う（v1 より後）
- 改造したコードを閉じたまま配られる
  - 緩和策: 受け入れる。緩いライセンスから強いライセンスへは、あとからでも変えられる。守りたい場面がはっきりしたら見直す
- 「点検の結果や報告書のひな形」の置き場所が決まっておらず、MIT と CC BY 4.0 のどちらか迷うファイルが出る
  - 緩和策: 置き場所が決まったら、README 第 8 節の一覧と `LICENSE-CONTENT.md` にパスを足す。迷うファイルは、顧客に渡るかどうかで決める
- `guide/` と、それ以外のガイダンスとで、出典の示し方が 2 通りになる
  - 緩和策: `guide/LICENSE-CONTENT.md` の示し方を取り込みのあとにどうするか、yokinist さんと決める（ADR 0002）

## 代替案

- **コードを MPL-2.0 にし、写して使うひな形は MIT-0 にする**: 改変したファイルを開いたままにさせられ、利用者のコードも巻き込まない。一方で、ライセンスが 3 種類になり、ファイルを足すたびにどちらに入れるかを判断する必要がある。役務提供の先の顧客に出典を伝えるという目的にも効かない
- **コードをひな形も含めてすべて MPL-2.0 にする**: ライセンスは 2 種類で済むが、ひな形を写すたびに MPL の表示を残す義務がつく。目的にも効かない
- **AGPLv3 または GPLv3 にする**: 利用者のリポジトリに写す部品が中心なので、利用者の法務の確認が重くなり、導入が止まりやすい。v1 にはサーバーがなく、AGPL のネットワークの条項が効く場面もない
- **CPAL などの、帰属の表示を求めるライセンスにする**: 求めるのは利用者の画面での表示で、報告書には届かない。広く使われておらず、GPL とも両立しない
- **すべて MIT にする**: 最も単純だが、取り込む `guide/data/` は CC BY 4.0 のまま残る。報告書に入れられても、出典を示す義務を求めにくい（MIT は全文を残す前提なので、文章の引用に向かない）
- **Apache-2.0 にする**: 特許の許諾があるが、取り込む 2 つのリポジトリとライセンスが変わる。CyberRiskScape のルールを取り込む場合も、帰属表示（`NOTICE`）を残せば MIT のリポジトリに置ける

## 今後の方向性

- 取り込みの PR で、`guide/LICENSE`・`guide/LICENSE-CONTENT.md`・`checker/LICENSE` が残っていることを確かめる
- `checklist.md` の書き出し・checker の Issue の本文・報告書のひな形に、出典の行を入れる
- 報告書のひな形の置き場所が決まったら、README 第 8 節と `LICENSE-CONTENT.md` にパスを足す
- CyberRiskScape のルールを取り込むことになったら、Apache-2.0 の `NOTICE` と帰属表示の置き場所を決める
- パスが増えて一覧の管理が大変になったら、[REUSE](https://reuse.software/) の `REUSE.toml` に移すことを検討する
- 改造版を閉じたまま配られて困る場面が出たら、コードのライセンスを見直す
