# Code for Security

セキュリティの専任がいない小さなプロジェクトが、コーディングエージェントといっしょに、自分のプロジェクトに基本の守りを入れるためのキットです。Code for Japan が OSS として作っています。

## なぜ作るか

- AI エージェントのおかげで、誰でも短い時間でサービスを作り、公開できるようになりました。課題を抱える当事者が、自分で試作することも増えています
- 一方で、API キーをコミットしてしまう、依存パッケージの既知の脆弱性を放っておく、といった事故は昔から変わらず起きています。メンバーが入れ替わるたびに、同じ事故が起きやすくなります
- 小さな非営利団体・自治体・シビックテックのプロジェクトには、何をやるべきかを調べ、ツールを選んで設定する余力がありません。そのため、対策をしないまま放っておかれがちです

足りないのは新しい診断のツールではなく、「自分のプロジェクトでは何が当てはまり、どう設定するのか」を埋める手助けです。Code for Security は、それをコーディングエージェントに任せます。

## 誰のためか

Code for Japan のプロジェクトと、同じくらいの規模の非営利団体・自治体・シビックテックのプロジェクトが対象です。

使うには、Claude Code・Codex・Cursor・GitHub Copilot などのコーディングエージェントが要ります。すでにエージェントで開発している人だけでなく、これをきっかけにエージェントを使い始める人にも使ってもらいたいと考えています。

## v1 でできること

v1 は 2026 年 12 月のイベントで公開します。プロジェクトのオーナーが、手元のコーディングエージェントといっしょに、次の 4 つを最後まで進められるようにします。

1. **点検表を完成させる**：エージェントがリポジトリを調べ、当てはまる項目を選びます。分からないことはオーナーに聞きます。項目ごとに、済み・未着手・対象外・リスクを受け入れる、を決めます
2. **脅威モデルを作る**：扱うデータや使っているサービスから、守るもの・入り口・脅威・残っている穴をまとめます
3. **回し続ける項目を知る**：コミットのとき（Gitleaks）、PR のとき（CodeQL・zizmor）、毎週（checker）など、続けて回す確認を一覧にします
4. **項目ごとに設定する**：エージェントがひな形を使って設定し、決まった手順で済んだことを確かめます。変更は、オーナーが 1 件ずつ承認します

1 回点検して終わりにせず、コミットのときの確認のような仕組みをプロジェクトに入れておくことを大事にしています。同じ穴を塞ぐ対策が重なってもかまいません。どれか 1 つが漏らしても、ほかで止まればよいからです。

それぞれの対策には、なぜ必要なのかを確かめられるよう、OWASP や IPA などの資料へのリンクを付けます。

### v1 では作らないもの

- CLI
- AI によるペネトレーションテストなどの診断エンジン（Strix・CAI など）
- 見つかったものを仕分けて直していく運用（トリアージ）。v1 の次に取り組みます
- 点検表を見るページ（Viewer）の作り直し
- ほかの人の OSS を見て回る取り組み

## いま使えるもの

| | 中身 |
|---|---|
| [はじめてのセキュリティ点検](https://yokinist.github.io/first-security-checkup/)（`guide/`） | プロジェクトに当てはまるもの（ログイン機能、個人情報など）を選ぶと、確かめるべき項目が優先度つきで出てくる点検表のページ |
| [weekly-security-checker](checker/)（`checker/`） | アカウントや organization のリポジトリを毎週まとめて調べ、指摘を非公開のリポジトリの Issue にまとめる GitHub Action（試験運用中） |

## リポジトリの構成

| パス | 中身 |
|---|---|
| `guide/` | 点検項目のデータと、点検表のページ |
| `checker/` | 毎週の横断チェックの GitHub Action |
| `docs/` | 設計の決定（ADR）と、v1 までの進め方 |

エージェントに読ませる点検の手順と、設定のひな形は、v1 に向けてこれから足します。

## 参加する

質問・指摘・提案は、[Issue](https://github.com/codeforjapan/code4security/issues) で受け付けています。イシューの立て方と決め方は [CONTRIBUTING](CONTRIBUTING.md)、v1 までの進め方は [ロードマップ](docs/roadmap-v1.md)、設計の決定とその理由は [`docs/adr/`](docs/adr/) にあります。

勧める対策やツールを変えるときは、必ず人がレビューします。検証されていない推奨を配ると、利用者が自分で調べるより悪い結果になるからです。
